# Backups and restore

`xui-backend backup global <archive>` creates a portable whole-system archive containing the configured PostgreSQL database, `backend.env` (including the original encryption key), every registered instance's `instance.env` and optional `metadata.json`, and canonical backend/bot systemd unit definitions plus their enabled/running state. This is a full secret bundle: it contains database credentials, bot tokens, backend tokens, and encryption keys. The archive is owner-only (`0600`) and parent directories are `0700`; store it on encrypted, access-controlled storage and transfer it over an authenticated encrypted channel. Verify a trusted out-of-band checksum after transfer. The database URL in the archived backend config is rebound to the target database during restore. The target database role and database must already exist, owned by the role in that target URL.

For a server move, use `xui-backend backup global-move <archive> --stop-source` or choose the move option in the menu. It stops active bot units first and then the backend worker, disables every previously enabled backend/bot unit so reboot cannot restart the source, and leaves the source services stopped and disabled after a successful archive. If the backup fails, it attempts to restore the original enabled and active state. The normal `backup global` command is a hot logical snapshot and does not stop the source. A destination restore requires the operator to confirm that the source backend and all source bots are stopped; the destination cannot verify the remote host.

The destination must be an empty application database or a pristine database produced by the fresh xui-backend installer. A pristine installer database is recognized only if its known bootstrap rows, `.invalid` panel placeholders, migration tables, and otherwise-empty commerce tables match exactly. Any changed seed configuration or user data makes restore refuse the target. On that pristine path, the importer locks the tables, rechecks the bootstrap state, replaces the public schema, and imports the archive in one PostgreSQL transaction. It never merges records. Existing target `backend.env` is preserved beside the live file as a mode-`0600` `.pre-global-restore-*` copy; the restored file keeps the target `DATABASE_URL` while restoring the source encryption key and other runtime settings.

Run `xui-backend restore global <archive> --dry-run` on the target first. Preflight checks the archive's SQL and file checksums, target schema/data, runtime units, and the source instance bearer token hashes inside a PostgreSQL transaction that it rolls back. It reports whether the database is empty or a pristine install and the backend's target loopback address. The target may have the installer's regular `backend.env` and identical disabled canonical unit files; unrelated or enabled/active units are refused. If the source port is busy, it selects an available loopback port and rewrites every restored bot `BACKEND_URL` and metadata URL to match. Restore rejects a non-loopback target listen address and refuses active or enabled target xui-backend services.

After the dry run, execute `xui-backend restore global <archive> --source-stopped --activate` to restore and activate, or omit `--activate` to leave every service inactive for review. The menu asks for the same source-stop confirmation and offers activation after the dry run. Restore checkpoints the pristine/empty target database and previous `backend.env` in a protected stage before import. If migrations, credential validation, runtime file installation, or activation fails, it attempts to reset the database and runtime config to that checkpoint; after successful reset, rerunning the same restore command is safe. If the process exits before cleanup or automatic rollback cannot finish, first stop and disable all target xui-backend units, then run `xui-backend restore global-recover <archive> <stage-path>` using the exact protected stage path reported by the command. Recovery validates that the stage belongs to that archive and target database, restores the checkpoint, removes partial instance files, and deletes the stage; then fix the cause and rerun restore. Restore imports the SQL, applies migrations, marks all unfinished provisioning work and unsent/uncertain Telegram outbox rows as quarantined, verifies panel/Telegram ciphertext against the archived encryption key and bot credentials against the restored database, installs the rebased config and canonical systemd units, then optionally starts only the backend and bot units that were active in the source. It verifies repeated systemd active state, backend `/healthz`, and a registered scoped admin credential before completing. Instance directories are traversable by the service account, while per-instance config remains private to that account. Quarantine is deliberate: panel create/update/delete and Telegram send outcomes may be uncertain at the snapshot point. Review remote panel state and notification history before releasing safe rows. Pending work in `ready` phase and outbox rows still in `pending` state have not been attempted and can be released after review with:

```sql
UPDATE work_items SET restore_quarantined=false WHERE status='pending' AND phase='ready';
UPDATE outbox SET restore_quarantined=false WHERE status='pending';
```

Rows in `running`, `create_attempted`, `sending`, `failed`, or `manual_review` require case-by-case reconciliation and must not be blindly replayed. If target activation fails, stop every target service before bringing the source back online; never run both writers at once. A restore error after the database transaction may leave the database restored and protected runtime files in the reported `.global-restore-*` stage for recovery. Database and filesystem changes cannot share one atomic transaction, so keep the source stopped and retain the archive until the target passes review.

Global restore moves the backend and its bot adapters; it does not migrate or alter 3x-ui. The restored server must reach the same panel instances and retain their client state. A panel migration is a separate operation and requires its own collision/readback plan. The archive checksum detects accidental corruption, not tampering; this format has no authenticity signature. Back up the archive separately before transferring it.

### Moving one bot instance between backend servers

This operation moves the instance's complete PostgreSQL dependency closure and bot configuration into an already-installed target backend; it does not copy only configuration. Both backends must be able to reach the **same existing 3x-ui panel**, which must retain that instance's remote clients and inbounds. The panel credential must have full-panel read access to the complete client list, inbound client stats, and inbound options; user-scoped or partial panel credentials cannot prove global email/UUID/subscription-ID uniqueness and must not be used for a move. The restore verifies panel client/inbound identities before importing; it does not migrate panel state or create a second set of clients. Configure the target backend to use the same panel API; the source recovery key in the protected archive is used to re-encrypt stored credentials with the target backend key.

1. On the source, run `xui-backend backup instance <slug> <archive>`. It stops the source bot, freezes deployment workers, drains in-flight API requests, provisioning operations, and notification sends with deployment-scoped locks, then writes the archive. On success it records the original bot active/enabled state, disables source bot startup, and leaves the source bot stopped and deployment frozen across reboot. If backup fails, it attempts to undo the freeze and restore the prior source state.
2. Securely transfer the archive to the destination. On the target, run `xui-backend restore instance <archive> <new-slug> --dry-run`. Preflight checks the target backend health and database, archive integrity, shared-panel remote identities, and whether the deployment can be imported into the shared backend. Resolve every reported collision before continuing.
3. Confirm the source bot and workers remain stopped. Run `xui-backend restore instance <archive> <new-slug> --source-stopped`; the CLI requires this explicit confirmation before activation. Restore imports the full instance state under a persisted transfer freeze, installs target config/unit with the target backend URL, and acquires the destination's exclusive transfer lease while the freeze remains set. It validates the restored scoped credential and designated administrator directly under that lease, starts the new bot, confirms it remains active, repeats the identity check, and verifies backend health. Only then does it release never-attempted ready work, release the transfer lease while the deployment is still frozen, and clear the transfer freeze. Normal API requests and workers cannot act during those checks or if lease release fails; uncertain work and notifications stay quarantined. The final unfreeze update is read back: a verified active state is treated as successful activation and reported as possibly visible if the write returned an ambiguous error, while a verified frozen state remains blocked and triggers cleanup. If the final write and readback cannot establish either state, the bot is left running for inspection and the command reports that activation is uncertain; inspect `transfer_frozen` before retrying because it may still block API/work or may already be active. If config installation or activation fails after DB import, the deployment remains frozen; after correcting the cause, rerun the exact same restore command with the same archive and slug to resume idempotently. Failed authentication, bot startup, health checks, lease release, or a verified failed unfreeze stop/disable the bot and freeze the deployment again.
4. Inspect the transfer with `xui-backend transfer inspect <new-slug>`. Review uncertain provisioning against the shared panel and uncertain sends against notification history. Only never-attempted pending work/outbox rows can be released with `xui-backend transfer release-safe <new-slug>`; the command enforces the safe status/phase/attempt checks. Reconcile uncertain rows individually; do not replay them blindly.

For rollback, first stop the destination bot and ensure no destination worker can act on the deployment. Then, on the source, run `xui-backend transfer resume <source-slug> --destination-stopped`; this requires explicit confirmation, verifies the source bot is inactive, and restores its original enabled/active state. Never run both copies as active writers. Keep the archive until the destination has passed review. `backup instance-config <slug>` is retained for config-only troubleshooting and does not contain customer or commerce state.

The database archive uses plain SQL to support PostgreSQL's `psql` restore path. Treat every backup archive as sensitive data. The manifest checksum detects accidental database dump corruption; it is not an authenticity signature.

## Source installer

There is no published release artifact for the new CLI yet, so avoid a `curl | sh` command that would point at a moving or stale artifact. Clone or check out the reviewed backend source on the server, then run from the repository root:

```sh
sudo ./install.sh
```

After this installer is merged to the default branch, the source-based pasteable command will be:

```sh
git clone https://github.com/AmirRnz/xui-backendhandler.git && cd xui-backendhandler && sudo ./install.sh
```

The installer builds the checked-out source's `cmd/xui-backend`, stages the binary outside `/usr/local/bin`, creates protected configuration and backup directories, and writes a systemd unit. On apt based hosts with the PostgreSQL 16 package available, it offers to install PostgreSQL 16 when the client tools are missing. It creates a dedicated `xui_backend` role and database only when neither name already exists, persists the generated database URL before creating either object, and applies migrations using the staged binary. It generates `BACKEND_PANEL_SECRETS_KEY` only for a confirmed fresh installer-managed database before any migration has applied. For an external database or a previously migrated database, a missing key stops setup with instructions to restore the original key; it never rotates a key that may decrypt stored tokens. Only after migrations succeed does it install the final executable and unit. A rerun resumes from the saved installer-managed database URL, verifies credentials and ownership, reapplies idempotent migrations, and finishes installation without replacing an existing binary or unit. Existing binaries and units are reused only when they exactly match the checked-out build and generated service definition; differing or symlinked files are left untouched and cause a clear stop. Backend and bot services stay stopped until an instance is configured. Required host tools are Go 1.25+, systemd, and PostgreSQL 16 tools; the installer is written for Linux hosts using systemd and apt when PostgreSQL needs installation.

The installer has been syntax checked with `bash -n`. The current Finland deployment was updated through the reviewed code-only delivery flow below; this paragraph does not claim that a fresh installer run has been completed. Review the script for the target OS before running it.

## Upgrading an installer-managed host

`upgrade.sh` is a staging and verification step. It accepts only an installer-managed installation with schema 012, writes a protected pre-update database dump, backend configuration, instance configuration, service units, and previous binary to an existing remote mount, builds the checked-out source, then rehearses migrations 013 and 014 against a disposable clone on the separately supplied PostgreSQL maintenance server. It removes the clone after verifying schema 014. The disposable maintenance role must be authorized to create and drop databases; provide it in a root-only env file as `DRY_RUN_DATABASE_URL=postgres://.../postgres?...`. The script does not stop or alter live services, the production database, or installed files. The current Finland host is already at schema 014, so this script refuses it until a schema-014-aware procedure is reviewed.

At the 2026-09-25 Finland inspection, no qualifying off-host backup mount or protected rehearsal environment was available. Do not substitute a local directory or the live database for either prerequisite.

Run `sudo ./upgrade.sh --backup-dir /mnt/off-host-backups --dry-run-db-env-file /root/xui-upgrade-dry-run.env`. The script verifies that the destination resolves to an NFS/CIFS/SSHFS mount and reads back the completed database dump. Before cutover, independently confirm that the selected mount is the intended off-host storage and that the backup directory and dump are visible from the recovery host; a remote filesystem type alone cannot prove the storage target or its independent availability. Review the emitted backup directory and complete the printed maintenance procedure during a planned window. Record active units first, stop instance units before the backend, install the staged binary atomically, migrate, check backend health and authenticated admin access, then restore only the previously active unit set. If a migration or health check fails, keep services stopped while restoring the saved database and files; restart only if database restoration is verified. Do not use the disposable database URL for the live migration. No live upgrade is automated because SQL restore and filesystem/systemd changes are not one atomic transaction.
